# CLAUDE.md: starter-react-shadcn

GitHub-Template mit dem Standard-Stack der Fabrik. Architektur und Meilensteine: `docs/ARCHITEKTUR.md`. Betrieb (lokal, Compose, Coolify, Caddy, Grenzen): `docs/BETRIEB.md`.
Diese Datei, `README.md` und bei Änderungen am Betrieb `docs/BETRIEB.md` pflegt jedes Ticket mit (`src/server/docs.test.ts` prüft Teile davon).

## Befehle

| Befehl | Was |
| --- | --- |
| `bun install` | Abhängigkeiten (Versionen fest in `bun.lock`) |
| `bun run dev` | `.env` aus `.env.example` anlegen, falls sie fehlt, Postgres aus `compose.yaml` starten (wartet auf healthy), dann parallel API mit `bun --watch` auf Port 3000 und Vite auf Port 5173 (leitet `/api` an 3000 weiter). Im Browser: http://localhost:5173 |
| `bun run build` | Oberfläche mit Vite nach `dist/client` bauen (erzeugt auch `src/client/routeTree.gen.ts` neu) |
| `bun run start` | Server ohne Watch starten (spielt Migrationen ein, dann Port): API, `/healthz`, `/probe` und die gebaute Oberfläche aus `dist/client` auf Port 3000. Vorher `bun run build` |
| `docker compose up --build` | Image bauen und mit Postgres starten: App auf http://localhost:3000 (Port 3000 frei, also ohne `bun run dev` daneben), Migrationen beim Start. `APP_URL` (Pflicht, kein Standardwert) aus der Umgebung des Rechners oder der `.env`, optional `BASIC_AUTH_USER`/`BASIC_AUTH_PASSWORD`, `ADMIN_EMAIL`/`ADMIN_PASSWORD` und die Seed-Passwörter ebenso. Im Container: `docker compose exec app bun run seed` bzw. `… user:create …`. Aufräumen: `docker compose down -v`. Image mit `NODE_ENV=production`, Cookie `Secure`: Safari kann die Anmeldung über `http://localhost` ablehnen (nicht in jedem Browser geprüft), Chrome und Firefox nicht |
| `bun run lint` | Biome (Lint und Format-Prüfung), danach `check:tokens` |
| `bun run check:tokens` | Findet feste Farben (hex, rgb, hsl, oklch u. a. und Tailwind-Farbklassen aus Palette und Stufe) außerhalb von `src/client/styles/tokens.css`, Exit-Code 1 mit `datei:zeile:spalte`. Mit Pfad (`bun run check:tokens src/client`) nur dort |
| `bun run format` | Biome schreibt Format und Import-Reihenfolge |
| `bun run typecheck` | `tsc --noEmit` |
| `bun test` | Unit-Tests unter `src/` (braucht `DATABASE_URL`, lokal Postgres aus Compose) |
| `bun run test:e2e` | Playwright (`e2e/playwright.config.ts`, Chromium): baut die Oberfläche, startet `bun run start` auf `APP_URL`, spielt Migrationen und `bun run seed` ein und prüft im Browser. Braucht Postgres, `SEED_ADMIN_PASSWORD` und `SEED_USER_PASSWORD` (lokal in `.env`) und einmalig `bunx playwright install chromium`. Port 3000 muss frei sein (kein `bun run dev` daneben). Einzelne Datei: `bun run test:e2e e2e/liste.spec.ts` |
| `bun run db:generate` | SQL-Migration aus `src/server/db/schema.ts` nach `drizzle/` erzeugen |
| `bun run db:migrate` | Migrationen einspielen, ohne den Server zu starten |
| `bun run user:create --email … --name … --role admin\|benutzer` | Benutzer anlegen, z. B. den ersten Admin. Passwort (mindestens 12 Zeichen) wird verdeckt abgefragt oder aus stdin gelesen. Spielt vorher die Migrationen ein |
| `bun run seed` | 30 synthetische Aufgaben anlegen bzw. auf den Seed-Stand zurücksetzen. Spielt vorher die Migrationen ein. Test-Konten nur mit `SEED_ADMIN_PASSWORD` (Test-Admin) bzw. `SEED_USER_PASSWORD` (Test-Benutzer), je mindestens 12 Zeichen, z. B. `SEED_ADMIN_PASSWORD=… SEED_USER_PASSWORD=… bun run seed`. Ohne sie (oder leer) keine Konten |

Bun-Version: `packageManager` in `package.json`, gilt auch für CI und `ARG BUN_VERSION` im `Dockerfile` (ein Test prüft den Gleichstand).

## Regeln

- **Fehlerformat:** Jede Fehlerantwort ist JSON `{error, fields?}` (`src/shared/api-error.ts`). `fields` nur bei ungültiger Eingabe (400), Schlüssel ist der Feldpfad, Wert eine Liste von Meldungen. Unerwartete Fehler werden geloggt und als 500 `{error: "Interner Fehler"}` ohne Details ausgegeben.
- **Validierung:** In Routen immer `validator` aus `src/server/validator.ts` statt `zValidator` direkt, sonst stimmt das Fehlerformat nicht. Schemas, die auch das Frontend braucht, liegen in `src/shared/`.
- **Rechte nur im Backend:** Rechteprüfung passiert ausschließlich serverseitig mit `requireAuth` (ohne Sitzung 401) und `requireRole("admin")` (andere Rolle 403) aus `src/server/auth/middleware.ts`. Das Frontend blendet höchstens zusätzlich aus.
- **Anmeldung:** `POST /api/auth/login` (`{email, password}`, falsch: 401), `POST /api/auth/logout` (204, löscht die Sitzung), `GET /api/auth/me` (`{user}`, ohne Sitzung 401). Rollen `admin` und `benutzer`. Sitzung: Cookie `sid` (`HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` bei `NODE_ENV=production`), in `sessions` steht nur der SHA-256 des Tokens. Laufzeit 7 Tage, bei Nutzung mit weniger als 3,5 Tagen Rest wieder 7 Tage. Passwörter mit `Bun.password` (argon2id), mindestens 12 Zeichen (`passwordSchema`).
- **Probe:** `GET /probe` nur mit `requireRole("admin")` (ohne Sitzung 401, Rolle `benutzer` 403, Fehlerformat `{error}`), Antwort 200 `{ok, checks}`. `loadSession` läuft dafür zusätzlich zu `/api/*` auch auf `/probe`. Die Checks stehen in `probeChecks` in `src/server/probe.ts` (`{name, run}`, `run` liefert `{ok, detail?}`), `ok` ist wahr, wenn alle ok sind, ein Check, der wirft, zählt als nicht ok. Im Starter ist die Liste leer (`{ok: true, checks: []}`). Bindet ein Projekt einen Fremddienst an, kommt dort ein Check mit Test im Replay-Modus dazu.
- **CSRF:** Ändernde Anfragen (alles außer GET, HEAD, OPTIONS) mit fremdem `Origin` lehnt `src/server/auth/csrf.ts` mit 403 ab. Erlaubt ist `Origin` gleich `APP_URL` oder `Sec-Fetch-Site: same-origin`. Formular-Content-Types und POST ohne Body brauchen zusätzlich einen passenden `Origin` (Hono `csrf()`), JSON ohne `Origin` (curl) geht durch.
- **Staging-Schutz:** Sind `BASIC_AUTH_USER` und `BASIC_AUTH_PASSWORD` gesetzt (beide nicht leer), verlangt `stagingBasicAuth` aus `src/server/auth/basic-auth.ts` (Hono `basicAuth`, zeitkonstanter Vergleich) bei jeder Anfrage Basic Auth, außer genau `GET /healthz`. Sie ist die erste Middleware in `createApp`, also vor CSRF, Sitzung, `/api/*`, `/probe` und der Oberfläche. Ohne Anmeldung oder mit falscher: 401 `{error: "Zugang nur mit Basic Auth"}` mit `WWW-Authenticate: Basic realm="Staging"` (`onError` gibt die fertige Antwort einer `HTTPException` mit `res` unverändert aus). Ohne die Variablen ist sie aus (lokal, Tests, Produktion beim Kunden), nur eine von beiden bricht den Start ab (`env.ts`), ein Doppelpunkt im Benutzer auch. Staging setzt beide.
- **Aufgaben-API** (alle Routen nur mit Anmeldung, sonst 401):
  - `GET /api/tasks`: Antwort `{items, total, page, pageSize}`, `total` ist die Zahl aller Treffer. Query: `page` (ab 1), `pageSize` (1 bis 100, Standard 10), `sort` (`dueDate`, `title`, `priority`, `status`, `createdAt`, mit `-` davor absteigend, Standard `-createdAt`), `status` und `priority` (mehrfach erlaubt: `?status=offen&status=erledigt`), `q` (Suchtext in Titel und Beschreibung, ohne Groß- und Kleinschreibung). Sortiert, gefiltert und geteilt wird in der Datenbank, letzte Sortierstufe ist `id`. Ohne Fälligkeit steht in beiden Richtungen am Ende.
  - `GET /api/tasks/:id` (`{task}`), `POST /api/tasks` (201 `{task}`, Ersteller ist der angemeldete Benutzer), `PATCH /api/tasks/:id` (nur gesendete Felder, mindestens eines, `{task}`): `admin` und `benutzer`.
  - `DELETE /api/tasks/:id` (204): nur `requireRole("admin")`, Rolle `benutzer` bekommt 403, auch bei unbekannter ID.
  - Unbekannte oder ungültige ID: 404 `{error: "Aufgabe nicht gefunden"}`. Ohne oder mit leerem Titel bzw. über 200 Zeichen: 400 mit `fields.title`.
  - Felder: `title` (1 bis 200 Zeichen, getrimmt), `description` (leer oder `null` wird `null`), `status` (`offen`, `in_arbeit`, `erledigt`, Standard `offen`), `priority` (`niedrig`, `mittel`, `hoch`, Standard `mittel`, Sortierung in dieser Reihenfolge), `dueDate` (`JJJJ-MM-TT` oder `null`), `createdBy` (Benutzer-ID, `null` nach Seed ohne Konten oder wenn der Benutzer gelöscht wurde).
- **Seed:** `scripts/seed.ts` ruft `seed()` aus `src/server/db/seed.ts`. Die 30 Aufgaben haben feste IDs, ein zweiter Lauf setzt sie auf den Seed-Stand zurück (alle Felder einschließlich `created_by` und `created_at`, Fälligkeiten relativ zum Tag des Laufs), eigene Aufgaben bleiben. Ersteller ist `seed-admin@example.test`, sobald es das Konto gibt (auch bei einem Lauf ohne `SEED_ADMIN_PASSWORD`), sonst `null`. Konten `seed-admin@example.test` (admin) und `seed-benutzer@example.test` (benutzer) nur, wenn das jeweilige Passwort gesetzt ist, ein bestehendes Konto bleibt unverändert. Ohne Variablen keine Konten. Die beiden Variablen liest `scripts/seed.ts` über ein eigenes `seedEnvSchema` (leer gilt als nicht gesetzt, sonst Passwortregel), sie gehören nicht ins Server-Schema in `src/server/env.ts`. Das erste Wort jedes Seed-Titels besteht nur aus ASCII-Buchstaben und ist kein Anfang eines anderen, damit die Titel-Sortierung unter jeder Collation gleich ist (ein Test prüft das).
- **Erster Admin:** `bun run user:create … --role admin` oder `ADMIN_EMAIL`/`ADMIN_PASSWORD` beim Start. Die Variablen greifen nur, wenn beide gesetzt sind und noch kein Admin existiert; danach aus der Umgebung entfernen (der Server weist im Log darauf hin). Ein zu kurzes `ADMIN_PASSWORD` verhindert den Start. Leere Werte gelten als nicht gesetzt.
- **Umgebung:** Neue Variablen ins Schema in `src/server/env.ts` und als Platzhalter in `.env.example`. Ein Test in `src/server/env.test.ts` (`compareEnvExample`) prüft beide Richtungen: Jeder Schlüssel des Schemas steht in `.env.example`, und dort steht nichts, was weder das Schema noch `SCRIPT_ONLY_KEYS` kennt. `SCRIPT_ONLY_KEYS` sind genau `SEED_ADMIN_PASSWORD` und `SEED_USER_PASSWORD` (nur von `bun run seed` und Playwright gelesen, leer in `.env.example`). Keine Secrets im Repo, `.env` ist ignoriert.
- **Datenbank:** Schema in `src/server/db/schema.ts`, danach `bun run db:generate`. Migrationen laufen beim Start, bevor der Port öffnet. Nur eine Instanz vorgesehen.
- **Sitzungen aufräumen:** `startSessionCleanup(db)` aus `src/server/auth/cleanup.ts` (Paket `croner`) läuft im Server-Prozess, kein Worker, kein externer Cron. Täglich um 3 Uhr (`SESSION_CLEANUP_PATTERN` = `0 3 * * *`, Zeitzone des Servers, im Image UTC) löscht `deleteExpiredSessions(db, now)` alle Zeilen aus `sessions` mit `expires_at` vor `now` und loggt die Zahl. Ein Fehler wird geloggt und abgefangen, der Server läuft weiter, der nächste Lauf bleibt geplant. Rückgabe ist der croner-Zeitplan (`stop()`, `nextRun()`, `trigger()`). Der Job hat absichtlich keinen croner-`name` (benannte Jobs sind prozessweit eindeutig, ein zweiter Aufruf würfe sonst), ein zweiter Aufruf plant also einen zweiten, unabhängigen Zeitplan, `index.ts` ruft die Funktion nur einmal. Kein Lauf beim Start, keine Umgebungsvariable. Nur für eine Instanz gedacht: Bei mehreren Instanzen liefe der Job in jeder (unschädlich, aber doppelt). Unabhängig davon löscht `validateSessionToken` eine abgelaufene Sitzung, sobald ihr Cookie noch einmal kommt.
- **Tests:** Unit-Tests liegen neben dem Code als `*.test.ts` unter `src/`. Tests mit Datenbank laufen gegen `DATABASE_URL` und leeren dort `users`, `sessions` und `tasks` (`resetAuthTables`, `resetTaskTables` in `src/server/test-helpers.ts`), also nie gegen eine Datenbank mit Daten laufen lassen, die man behalten will. Migrationen spielt `migratedTestDb` je Datenbank nur einmal pro Testlauf ein (zwei gleichzeitige Läufe kollidieren auf leerer Datenbank). `src/server/test-helpers.test.ts` legt dafür eine leere Wegwerf-Datenbank `migrate_test_…` an und löscht sie wieder, der Benutzer aus `DATABASE_URL` braucht also das Recht `CREATEDB` (in Compose und CI gegeben). Vor dem Push die Tests einmal gegen eine frische Datenbank laufen lassen, wie in CI. Ändernde Testanfragen ohne Body (z. B. `DELETE`) brauchen den Header `Origin` gleich `APP_URL`, sonst greift CSRF. Tests, die Prozesse starten oder Datenbanken anlegen, bekommen 20 Sekunden Timeout. Dateipfade aus `import.meta.url` immer über `fileURLToPath(new URL(…))` aus `node:url`, nie über `.pathname` (prozent-kodiert, scheitert in Ordnern mit Leerzeichen oder Umlaut), `src/server/file-paths.test.ts` prüft das. `src/server/first-admin.test.ts` startet den Server gegen frische Datenbanken `first_admin_test_…` (AK10: ohne ersten Admin keine Anmeldung, danach schon) und löscht sie wieder.
- **Design-Tokens:** `src/client/styles/tokens.css` ist die einzige Stelle für Farben, Schrift (`--font-sans`), Radien (`--radius`) und Abstände (`--spacing`), als CSS-Variablen auf `:root`. Werte: neutrale shadcn-Palette, die Primärfarbe `--navy` ist ein **Platzhalter**, bis der Wert aus dem Designsystem abgestimmt ist. `index.css` ordnet die Variablen Tailwind zu (`--color-primary: var(--primary)` usw.) und enthält selbst keine Werte. Die Tailwind-Standardpalette ist abgeschaltet (`--color-*: initial`), ihre Klassen erzeugen kein CSS. Komponenten und Seiten nutzen nur Token-Klassen (`bg-primary`, `text-muted-foreground`, `bg-overlay`, `rounded-md`, `p-4`). Neue Farbe: Variable in `tokens.css`, Zuordnung in `index.css`, dann die Klasse nutzen. Eine andere Token-Datei mit denselben Variablen ändert Farben und Schrift überall (belegt durch `e2e/tokens.spec.ts`). Der Block `.dark` in derselben Datei setzt alle Farb-Tokens aus `:root` (auch `--overlay`) für das dunkle Schema, `--primary` und `--ring` (ebenso `--sidebar-primary` und `--sidebar-ring` der Seitenleiste) kommen dort wie hell aus `--navy` (dunkel ein helleres Navy, ebenfalls Platzhalter). Neue Farbe also in beiden Blöcken anlegen, `src/client/styles/tokens.test.ts` prüft, dass `.dark` genau die Farb-Tokens aus `:root` setzt. Die Regel „Farben nur in `tokens.css`“ gilt auch für das dunkle Schema: `dark:`-Klassen in Komponenten nur mit Token-Klassen, meist braucht es sie gar nicht.
- **Farbschema:** Wahl `hell`, `dunkel` oder `system` (Standard, folgt `prefers-color-scheme`), gespeichert in `localStorage` unter `theme`, nicht im Benutzerkonto. Dunkel heißt: `<html>` trägt die Klasse `dark`, dann gilt `.dark` aus `tokens.css` und die Variante `dark:` (`@custom-variant dark` in `index.css`, Klasse statt Media-Query). `src/client/lib/theme.ts`: `readTheme` (ungültige oder fehlende Werte und gesperrter Speicher ergeben `system`), `saveTheme`, `applyTheme`, `isDark`, `systemPrefersDark`, `watchSystemTheme`. Das Skript im `<head>` von `index.html` setzt die Klasse vor dem ersten Rendern nach denselben Regeln, `theme.test.ts` führt es aus und vergleicht mit `theme.ts`, bei einer Änderung also beide anpassen. Der Umschalter `ThemeToggle` (`components/theme-toggle.tsx`, Knopf mit zugänglichem Namen „Farbschema wechseln“, Lucide `Sun`/`Moon`, Menü mit den Radio-Einträgen „Hell“, „Dunkel“, „System“) steht auf der Anmeldeseite (und der 404-Seite) in der Kopfzeile von `routes/__root.tsx`, im geschützten Bereich im Fuß der Seitenleiste (`components/app-sidebar.tsx`), auf jeder Seite also genau einmal. Bei `system` folgt die Seite einem Wechsel im Browser ohne Neuladen. Die Seiten füllen die Höhe unter der Kopfzeile mit `flex-1`, nicht mit `min-h-svh`.
- **check:tokens:** Teil von `bun run lint` und damit der CI. Prüft alle `.ts`, `.tsx`, `.js`, `.css`, `.html` im Repo außer `node_modules`, `dist`, `scripts/fixtures`, `e2e/fixtures` und den Playwright-Ausgaben (`e2e/test-results`, `e2e/playwright-report`), auch Kommentare. Also auch in Kommentaren und Tests keine Farbwerte oder Palette-Klassen ausschreiben (der Test von `check:tokens` liest seine Erwartungen deshalb aus den Beispieldateien).
- **shadcn/ui:** Komponenten liegen als Quelltext in `src/client/components/ui/` und dürfen angepasst werden. Neue Komponenten mit der shadcn-CLI (`components.json`) oder von Hand nach der Vorlage, danach `bun run lint`: Feste Farben aus der Vorlage (z. B. weiße Schrift, schwarzes Overlay) durch Tokens ersetzen, neue CSS-Variablen der CLI aus `index.css` nach `tokens.css` verschieben. DropdownMenu enthält zusätzlich `DropdownMenuRadioGroup` und `DropdownMenuRadioItem` aus der Vorlage (für den Umschalter). Bisherige Abweichungen: Button `destructive` nutzt `text-destructive-foreground`, Overlay von Dialog, AlertDialog und Sheet `bg-overlay`. Sheet nur mit den Seiten links und rechts. Sidebar: siehe Regel „App-Hülle“. Auswahlfelder in Formularen sind `NativeSelect` (echtes `<select>`, geht direkt mit `register()`).
- **Oberfläche und API:** Aufrufe nur über `api` aus `src/client/lib/api.ts` (Hono-RPC, Typen aus `AppType`) und `unwrap(...)`: gibt den Body der Erfolgsantwort zurück (204: `null`) und wirft sonst `ApiError` mit `status`, `message` (= `error` der API) und `fields`. `status` 0 heißt Server nicht erreichbar. Daten über TanStack Query, 4xx wird nicht wiederholt, eine 401 aus einer Abfrage setzt den Benutzer auf `null` und leitet zur Anmeldung.
